## 원인 ① 하나카드 취소(cancel) 룰 부재 — +71,603원 과다

`card_filters.json`의 cancel 타입 필터는 `shinhancard_8423_cancel_v1`, `lottecard_check_cancel_v1` **2개뿐**.
하나카드(`com.hanaskcard.paycla`)는 approval 룰만 있어 취소 알림이 전부 무시된다.

### 1-a. 하나 매직 9207 — 승인 후 즉시 취소 (+48,000)

7월 12일 19:33에 **승인·취소 알림이 같은 시각에 쌍으로** 도착했다.

```
07-12 19:33  T:(결제) 48,000원      B:쿠팡이츠 / 신용(일시불,9*0*) / 07.12 19:33 / 누적이용금액 992,977원
07-12 19:33  T:(결제취소) -48,000원  B:쿠팡이츠 / 신용(일시불,9*0*) / 07.12 19:33 / 누적이용금액 944,977원
```

승인은 `hanacard_magic_9207_approval_v1`(`title_regex: ^\(결제\)\s*(?<amount>[0-9,]+)원`)에 매칭되어 +48,000 적재.
취소는 title이 `(결제취소)`라 어떤 룰에도 안 걸림 → 차감 안 됨.
카드사 앱은 순액 0으로 처리하므로 MyCard만 48,000원 많다.

### 1-b. 하나 SK브로드밴드 0179 — 매출취소 (+23,603)

```
07-02 14:19  T:매출취소 안내  B:[매출취소안내] 01일 / -23,603 원 / 쿠팡전용_KCP
```

카드사 앱에는 `쿠팡전용_KCP -23,603원 (2026.06.28)`으로 7월 실적에서 차감되어 있다.

**주의: 이 알림에는 카드 식별자(`9*0*` / `0*7*`)가 없다.** 하나카드 2장 중 어느 카드인지 알림만으로 특정 불가.
룰을 만들 때 카드 귀속을 정할 방법이 없으므로, 별도 처리(사용자 확인 또는 단일 그룹 처리)가 필요하다.

### 1-c. 룰 공백 (현재는 차이 없음)

```
07-16 22:02  T:결제  B:(0*7*)차*욱님 07/16 22:02/해외승인/KRW 29,290/Norton *AP1701942015
```

해외승인 포맷(`(0*7*)...KRW 29,290`)은 기존 approval 룰(`^(결제) N원`)과 형식이 달라 미매칭.
카드사 7월 실적에도 아직 없어서 현재 차이를 만들지는 않지만, 반영되면 −29,290원 부족이 발생한다.

## 원인 ② Room dedupe로 알림 자체가 유실 — 네이버 현대카드 −21,890원

**"알림이 빠진 경우"에 해당하는 유일한 실거래 케이스.**

```
07-23 14:30:26  com.hyundaicard.appcard
  T:현대카드   B:자동납부 승인 차*욱님 SK브로드밴드 21,890원
  → rawdump/DB에 남은 것은 2026-05-23 14:30:00 건뿐
```

`NotificationEntity`의 UNIQUE 인덱스가 `(pkg, title, text, bigText)`인데,
이 자동납부 알림 **본문에 날짜·거래번호가 전혀 없어** 매달 문자열이 완전히 동일하다.
→ 5월 건이 먼저 적재된 뒤 6월·7월 건은 `insert`가 `-1`을 반환하며 버려졌다.
`CardNotificationListener`는 `newId == -1`이면 `RawDump.appendObject()`도 건너뛰므로
**`raw_notifications_2026.jsonl`에도 남지 않아 `rebuildFromRaw`로도 복구 불가**하다.

카드사 앱 기준 네이버 현대카드 7월 내역에는 `SK브로드밴드 21,890원 (7.22)`이 포함되어 있다.

### dedupe 유실 전수 조사

7월 카드사 패키지 알림 266건 → 3ms 간격 중복 발송을 접으면 논리적 이벤트 201건.
그중 **65건이 과거 알림과 dedupe 키 충돌로 유실**됐고, 실거래는 위 21,890원 **1건**뿐이며
나머지 64건은 전부 광고·명세서·포인트 안내다.

참고로 하나카드는 동일 알림을 **3ms 간격으로 2번** 발송하는데, 이 중복은 dedupe가 정상적으로 제거하고 있다
(즉 dedupe 자체는 필요한 기능이며, 제거가 아니라 키 보강이 답이다).

## 원인 ④ SKT 자동납부 룰 제외 — SK 현대카드 −39,650원

```
07-14 14:51  T:현대카드  B:자동납부 승인 차*욱님 SKT 07월-**23-2287 39,650원
```

`hyundaicard_autopay_approval_v1`의 `body_regex`가
`자동납부 승인\s+\S+\s+(?<merchant>SK브로드밴드)\s+(?<amount>[0-9,]+)원`으로
**merchant를 `SK브로드밴드`로 하드코딩**해 SKT 자동납부를 의도적으로 제외한다(v1.1.0.0 변경).

또한 이 필터의 `card_company`가 `네이버 현대카드`인데, SK브로드밴드 자동납부는 카드사 앱에서
**네이버 현대카드** 소속이고 SKT 자동납부는 **SK 현대카드** 소속이다 — 두 자동납부는 서로 다른 카드에 귀속된다.

## 원인 ⑤ 시점 차이 (버그 아님) — 네이버 현대카드 +24,600원

```
07-29 17:36  네이버 현대카드 승인 24,600원 일시불  쿠팡
```

MyCard는 승인 알림 즉시 반영하지만 카드사 앱은 **매출표 접수일** 기준으로 목록에 올린다.
카드사 앱에는 아직 없으므로 MyCard가 틀린 것이 아니라 반영 시점이 앞선 것이다.

같은 이유로 두 앱의 **날짜가 최대 2일까지 어긋난다**. 예: 코스트코 157,600원 → 알림 07-25 19:26 / 카드사 앱 07.27.
월 경계에 걸린 거래는 이 차이만으로도 소속 월이 달라질 수 있다.

검산: `149,700 − 24,600 + 21,890 = 146,990` = 카드사 앱 값과 정확히 일치.

## 권고 수정안 (우선순위)

| # | 조치 | 효과 | 난이도 |
|---|---|---|---|
| 1 | `hyundaicard_sktm_ed_approval_v1`의 `SKT-M`을 `SKT[-\s]?M` 등으로 완화 (신·구 포맷 동시 수용) | +179,350 즉시 회복 | 낮음 (필터만) |
| 2 | 하나카드 cancel 룰 2종 추가 — `^\(결제취소\)\s*-?(?<amount>[0-9,]+)원`(카드 식별 가능), `매출취소안내`(식별 불가) | +71,603 과다 해소 | 낮음~중 (귀속 정책 필요) |
| 3 | SKT 자동납부 룰 추가 (`card_company: SK 현대카드`) | +39,650 회복 | 낮음 (필터만) |
| 4 | Room UNIQUE 키에 `ts` 포함 (`(pkg,title,text,bigText,ts)`) 또는 dedupe를 "동일 키 + N초 이내"로 완화 | 매월 반복 알림 유실 방지 | 중 (DB 마이그레이션) |
| 5 | 하나카드 해외승인 포맷 룰 추가 | 향후 −29,290 방지 | 낮음 |

### 4번에 대한 보충

현재 dedupe는 **하나카드의 3ms 중복 발송을 막는 실질적 역할**을 하고 있으므로 단순 제거는 안 된다.
`ts`를 키에 넣으면 3ms 차이 중복이 되살아나므로, **"동일 (pkg,title,text,bigText) + ts 차이 5초 이내"만 중복으로 간주**하는
방식이 안전하다. 이는 `@Insert(IGNORE)` 대신 삽입 전 조회가 필요하다.

또한 `newId == -1`일 때 `RawDump`에 기록하지 않는 현재 동작 때문에 **유실된 알림은 `rebuildFromRaw`로도 복구되지 않는다.**
`raw_notifications_all_*.jsonl`에는 원본이 남아 있으므로, 복구가 필요하면 그 파일을 소스로 재구성하는 경로가 별도로 필요하다.

### 잔존 이슈

1. **이미 유실된 6·7월 자동납부 21,890원은 자동 복구되지 않는다.**
   `insert`가 `-1`을 반환하면 `RawDump`에도 쓰지 않으므로 `raw_notifications_2026.jsonl`에 원본이 없고,
   `rebuildFromRaw`로는 되살아나지 않는다. 원본은 `raw_notifications_all_2026_06/07.jsonl`에 존재.
   → 단건이면 ⋮ → **항목 추가**로 수동 입력, 근본 해결은 all-dump 재적재 경로 신설이 필요하다.
2. **`하나카드 매출취소` 그룹은 합계가 음수**다. 전체 총계는 정확해지지만 목록에 음수 그룹이 노출된다.
   UI 수용 여부는 실사용 확인 후 판단.
3. **두 앱의 날짜 기준이 다르다** (MyCard=승인 시각 / 카드사=매출 접수일, 최대 2일 차이).
   월 경계 거래는 이 차이만으로 소속 월이 달라질 수 있어 완전 일치는 구조적으로 불가능하다.

## 재현용 스크립트

조사에 사용한 스크립트는 세션 스크래치패드에 있으며 영구 보관하지 않았다. 재현 절차:

1. `adb pull /sdcard/Documents/MyCard/raw_notifications_all_2026_07.jsonl`
2. `adb pull /sdcard/Documents/MyCard/raw_notifications_2026.jsonl`
3. `adb exec-out "run-as com.example.mycard cat /data/data/com.example.mycard/databases/notifications.db" > notifications.db`
   (`adb shell ... cat > /sdcard/...` 는 0바이트가 되므로 **`exec-out` 필수**)
4. jsonl은 pretty-print 다중행이므로 `JSON.parse`가 아닌 **brace-balanced 스캐닝**으로 객체 분리
5. Java 정규식 `(?<name>)` → Python `(?P<name>)` 치환 후 `CardParser.tryMatch` 동작 재현

> DB는 **읽기만** 했다. `adb push` / `run-as cat >` 로 DB에 쓰는 행위는 파일 손상 → Room 자동 삭제로
> 전체 알림 이력이 날아가므로 절대 금지 (CLAUDE.md 규칙).
